# MCU Bootloader 模板 —— 软件设计需求

版本：v0.2（需求冻结稿）
日期：2026-09-02

## 1. 项目定位

本仓库是一个**可移植的 MCU bootloader 模板**，从零实现、自洽交付，不依赖任何外部仓库代码。它是一个**完整的项目**，不是库——内部模块直接函数调用，没有为"被集成"而设的抽象层。

## 2. 总体架构

### 2.1 项目组成

| 部分 | 职责 |
|---|---|
| 启动与主流程 | 上电初始化、启动决策（外部触发 / 升级标志 / CRC 校验 / 跳转） |
| UDS + ISO-TP | 诊断服务状态机与 CAN 传输层（纯逻辑，可在 PC 上编译测试） |
| 升级通道接口 | 项目内部定义的通道抽象（可插拔，见 2.2），当前实现为 CAN |
| flash 驱动 | app 区擦写、参数区读写（含双副本策略） |
| CRC | 上电全量校验；F103 优先用硬件 CRC 外设，其它芯片可换软件查表 |
| 跳转 | 关闭中断、设置 MSP、向量表重映射、跳转（bsp 实现） |

**移植方式**：换芯片/内核 = 重写 bsp 目录（启动文件、CAN/flash/CRC 驱动、跳转实现），项目主体不动。这是"项目换板级支持包"，不是"实现库接口"。

**纯逻辑模块与硬件解耦的唯一原因**：让 host 单元测试能在 PC 上编译（ISO-TP/UDS 解析、CRC 查表、header/参数区结构）。这是交付物的一部分，不是库化设计；测试完照常编进固件。

### 2.2 升级通道

- 升级通道是**项目内部的可插拔接口**（这是产品需求，不是库化设计），主流程面向接口编程，不绑定具体协议。
- 第一参考协议：**UDS over CAN（ISO 15765-2 ISO-TP）**。
- 换协议/换总线 = 替换通道实现 + 对应驱动，项目主体不动。

## 3. 功能需求

### 3.1 启动流程

boot 上电后按以下顺序决策：

1. 检查外部触发条件（如按键电平/引脚状态）——调试/救砖入口；
2. 检查参数区"升级请求标志"——app 主动请求入口；
3. 均不满足 → 全量 CRC 校验 app → 校验通过则跳转，失败则停在 boot 等升级。

### 3.2 app 有效性判断

- **每次上电对 app 区做全量 CRC32 校验**，与固件 header 中记录的 CRC 比对。
- F103 优先使用硬件 CRC 外设，无硬件 CRC 的 MCU 可换软件查表实现（函数接口不变）。
- 上电校验耗时（约 220KB @ 72MHz，几十至一两百毫秒）作为已知代价被接受。

### 3.3 flash 参数区（boot↔app 通信区）

- 位置：flash 末尾两页（双副本 A/B），2KB × 2。
- 存放：升级请求标志，及将来可扩展的升级参数（固件长度、版本等）。
- **双副本策略**：写入先更新副本 A → 校验 → 再更新副本 B；读取时取 CRC 有效的一份。保证"擦除中途断电不误判"。
- 参数区的页大小、擦写接口由 bsp 提供。

### 3.4 固件格式

固件文件 = **固定长度 header + 数据体**，与传输协议无关。header 字段：

- magic（识别自家固件）
- 固件长度
- CRC32（数据体）
- 版本号
- 目标信息（入口地址或分区 ID）
- header 自身 CRC

header 采用固定大小，字段未用的空间预留。

**职责切分（三层，不得混淆）：**

| 层 | 职责 |
|---|---|
| 固件格式（磁盘产物） | 自描述：多长、什么版本、是否完整 |
| 传输协议（线上字节流） | 上位机把 header 拆进专属帧传输，完整性由协议保证 |
| 启动有效性 | boot 上电消费 header 做全量 CRC 判断 |

UDS 传输中 header 信息使用专属帧（如 0x34 请求下载携带元数据），不与 0x36 数据帧混流。

### 3.5 升级入口（双入口）

1. **外部触发**：按键/引脚条件满足时 boot 停留等待升级（调试、救砖用）。
2. **app 主动请求**：app 收到升级指令 → 通过 app 侧请求库写参数区标志 → 软复位 → boot 检测标志后进入升级模式。boot 不与运行中的 app 直接交互，只面对静态 flash。

### 3.6 UDS 服务清单（冻结）

| SID | 服务 | 备注 |
|---|---|---|
| 0x10 | 会话控制 | 进/出扩展会话 |
| 0x27 | 安全访问 | 流程桩（见 3.7） |
| 0x31 | 例程控制 | 触发擦除 app 区、CRC 校验 |
| 0x34 | 请求下载 | 携带固件元数据（专属帧语义） |
| 0x36 | 传输数据 | 固件数据体 |
| 0x37 | 退出传输 | 升级收尾 |
| 0x3E | 诊断仪在线 | 会话保活 |
| 0x22 | 读 DID | boot/app 版本号等 |
| 0x11 | ECU 复位 | 升级完复位进新固件 |

其余服务（0x19、0x14、0x2E 等）全部不实现。

### 3.7 安全访问策略

- 0x27 流程状态机完整（seed/key 交互、会话约束），但密钥算法为**模板占位实现**。
- 配置头设置 BL_SECURITY_IMPLEMENTED 宏：
  - 默认 0：桩模式，0x27 直接解锁；
  - 设为 1 时，若密钥算法仍是占位实现，**编译期报错**强制集成者替换。
- 此规则写入文档安全章节，量产前必须替换算法。

## 4. flash 分区表（STM32F103 高密度，256KB，页 2KB）

| 分区 | 起始地址 | 大小 | 用途 |
|---|---|---|---|
| boot | 0x08000000 | 32KB | bootloader 本体 |
| app | 0x08008000 | 约 220KB | 应用固件（header + 数据体） |
| 参数区 A | 0x0803F800 | 2KB | 状态/标志 双副本之一 |
| 参数区 B | 0x0803FC00 | 2KB | 状态/标志 双副本之二 |

- boot 预留 32KB 余量，为将来加签名/日志等扩展，避免动分区表（动分区表 = 已发布 app 全部失效）。

## 5. 限制声明

- **单 app 区，无防变砖设计**：升级过程中断电可能导致设备无法启动，需外部工具（调试器/CAN 上位机）恢复。此限制为架构的明确边界，将来升级到 A/B 双区方案时接口预留不回退。
- **无运行期日志输出**：boot 调试暂全靠调试器断点，不实现 SWO/UART 日志（将来按需增加）。

## 6. 目标硬件

- 参考移植平台：**STM32F103 高密度系列**（RC/RD/RE，含 bxCAN 外设）。
- bsp 参考实现锚定 F103；其他 MCU 重写 bsp 目录。
- 目标内核架构：裸机 Cortex-M 为主，多内核（跳转处理在各芯片的 bsp 内）。

## 7. 构建与工具链

### 7.1 目录结构

```
mcu/
|-- bootloader/      boot 本体（主流程 + UDS/ISO-TP + 升级通道实现）
|-- app/             app 侧（请求库 + app 例程）
|-- bsp/             板级支持包（F103 启动文件、CAN/flash/CRC 驱动、跳转）
`-- project/
    `-- MDK/         MDK 工程（引用源码，将来 IAR 同级）
host/
|-- flasher/         Python 烧录上位机
|-- packer/          post-build 固件打包脚本（Python）
`-- tests/           主机单元测试（纯逻辑模块在 PC 上编译运行）
docs/
`-- protocol/        协议规格、分区表、升级流程
```

### 7.2 构建体系

- MCU 端：**MDK 工程**，位于 mcu/project/MDK/，工程文件以相对路径引用 mcu/ 下源码，不复制源码。加新 IDE 平台 = 加 mcu/project/<IDE>/。
- PC 端：主机单元测试用 CMake 独立构建（CRC 查表、header 解析、ISO-TP/UDS 状态机、参数区双副本逻辑），仅作开发期验证，不作为交付构建系统。
- post-build 打包脚本为 **Python**，挂在 MDK after-build 命令执行，将链接产物加 header 生成升级文件。

## 8. 交付物

1. boot 固件源码（主流程 + UDS/ISO-TP + F103 bsp）
2. app 侧请求库（参数区结构 + 写标志/软复位 API，boot/app 共用同一份结构定义）
3. Python post-build 打包脚本
4. Python 烧录上位机
5. 主机单元测试
6. 文档：协议规格、分区表、升级流程、移植指南
